# M4-05 · 上下文工程（Context Engineering）

> 📅 内容基准：2026-11 ｜ ⏱️ 时效性：中 ｜ 🔁 下次复核：2027-05
>
> 一句话结论：**模型能力之外，决定效果的最大变量是"你往上下文里放了什么、放了多少、按什么顺序放"。**

---

## 一、为什么 Prompt Engineering 不够用了

2023–2024 年，大家关注"怎么写提示词"：加角色、加示例、加"让我们一步步思考"。
到了 2025–2026 年，Agent 要连续跑几十轮、调用工具、读写文件、跨会话工作，问题变成了：

- 上下文窗口再大也会被塞满，而且**塞得越多，模型对关键信息的注意力越差**（俗称 context rot / 上下文腐化）。
- 工具返回的长日志、检索到的整篇文档，会挤掉真正重要的指令。
- 多轮对话里，早期的目标和约束会被后来的内容稀释。
- Token 就是钱：上下文越长，延迟和成本越高。

于是关注点从"提示词技巧"迁移到**上下文工程（Context Engineering）**：把上下文当成一个需要设计的系统，而不是一段随手写的文字。

> 相关阅读：Anthropic《Effective context engineering for AI agents》<https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents> · Chroma《Context Rot》研究 <https://research.trychroma.com/context-rot>

## 二、上下文由什么组成

| 组成 | 典型内容 | 变化频率 | 设计要点 |
|------|----------|----------|----------|
| **系统指令** | 角色、目标、约束、输出格式 | 低 | 稳定、短、可复用；项目级规则应外置成文件 |
| **工具定义** | MCP / function calling 的 schema | 低 | 只暴露当前任务需要的工具，避免"工具太多选错" |
| **记忆** | 用户偏好、项目决策、历史结论 | 中 | 显式写入 + 按需读取，不要全量回灌 |
| **检索内容** | RAG 文档、代码片段、网页 | 高 | 先筛后放，控制条数与长度，标注来源 |
| **对话历史** | 多轮消息、工具结果 | 高 | 定期压缩/摘要，保留决策与未完成事项 |
| **技能/知识** | Skills、规则文件、示例 | 低 | 渐进式披露：先给目录，需要时再展开 |

一个实用的判断：**这段内容在"每一次"调用里都必须存在吗？** 不是的话，就不要常驻上下文。

## 三、六个核心手法

### 1. 分层：稳定内容外置

把项目规则、架构说明、编码规范写进文件（`AGENTS.md` / `CLAUDE.md` / `.cursor/rules`），而不是每轮对话重复粘贴。
好处：可版本管理、团队共享、不占对话预算。

### 2. 预算：给上下文设上限

给每类内容分配 token 预算，例如：

```
系统规则   ≤ 2k
工具定义   ≤ 3k
检索内容   ≤ 8k
历史对话   ≤ 6k
留给输出   ≥ 4k
```

超出预算时，优先裁剪"可重新获取"的内容（日志、原文），保留"不可再生"的内容（目标、约束、决策）。

### 3. 压缩：摘要 + 检查点

长任务跑到一定轮次后，把历史压缩成结构化摘要：

```markdown
## 任务状态
- 目标：
- 已完成：
- 当前阻塞：
- 关键决策：
- 下一步：
```

Claude Code 等工具会在上下文接近上限时自动 compact；团队实践里也可以显式要求 Agent"先总结再继续"。

### 4. 隔离：用子 Agent 保护主上下文

把"读一大堆文件/日志"的脏活交给子 Agent，只把**结论**带回主会话。
这是多 Agent 架构真正的价值之一：不是并行更快，而是**上下文更干净**。

### 5. 渐进披露：Skills 的正确用法

Skill 不应该一次性把全部内容灌进上下文。好的做法是：
- 元数据（名称 + 一句话说明）常驻，让 Agent 知道"有这个能力"；
- 命中任务后再加载正文；
- 长文档拆成按需读取的片段。

### 6. 结构化：让模型好定位

- 用清晰的标题、列表、XML/JSON 标签区分内容类型；
- 把"指令"和"数据"显式隔开（防止提示注入）；
- 关键约束放在开头或结尾，别埋在中间。

## 四、常见反模式

| 反模式 | 后果 | 改法 |
|--------|------|------|
| 把所有文档一次性塞进 prompt | 成本高、注意力分散、效果反而下降 | 检索 + 裁剪 + 分步 |
| 每轮重复贴同样的规则 | 挤占预算、容易前后矛盾 | 外置为规则文件 |
| 工具返回结果原样保留 | 日志淹没关键信息 | 只保留摘要/差异/错误行 |
| 无限增长的历史 | 早期目标丢失、跑偏 | 摘要、检查点、重开子任务 |
| 让 Agent 自己决定读哪些文件 | 可能读偏、读爆 | 给目录 + 明确读取范围 |
| 只优化 prompt 不看上下文 | 调了半天没效果 | 先看实际发给模型的完整上下文 |

> 💡 调试 Agent 时，第一件事不是改 prompt，而是**把真实请求的完整上下文打印出来看一眼**。

## 五、和 RAG、MCP、Skills 的关系

```
上下文工程 = 决定"放什么"
├── RAG       → 从外部知识里"取"什么
├── MCP       → 从外部系统里"调"什么（工具结果也是上下文）
├── Skills    → 把流程/知识"封装"成可按需加载的模块
└── Memory    → 跨会话"记住"什么
```

它们不是互相替代，而是同一个问题的不同侧面：**在正确的时刻，把正确的信息，以正确的形式，放进有限的上下文。**

## 六、怎么判断上下文设计得好不好

1. **可复现**：同样的输入，效果稳定，不靠运气。
2. **可解释**：知道模型看到了什么才做出这个决定。
3. **可压缩**：去掉一半上下文，关键结论不丢。
4. **可评估**：有固定的测试集和指标（见 [M4-06 评测与质量闭环](./06-evaluation.md)）。

## 七、历史沿革

- **2023**：Prompt Engineering 成为显学，关注提示词模板、few-shot、CoT。
- **2024**：RAG 工程化；长上下文（100 万 token 级）出现，"把整本书塞进去"成为可能。
- **2025**：Agent 化让上下文管理成为瓶颈；context rot 研究出现；compaction、子 Agent、memory 成为产品能力；"context engineering" 一词开始流行。
- **2026**：上下文工程成为 Agent 工程的核心技能；Skills / Plugins 用渐进披露管理知识；多会话编排（Agent Teams）把"上下文隔离"变成架构原则。
