# M4-06 · 评测与质量闭环

> 📅 内容基准：2026-11 ｜ ⏱️ 时效性：中 ｜ 🔁 下次复核：2027-05
>
> 一句话结论：**没有评测的 AI 系统只能靠感觉；评测不是为了排名，而是为了在模型、提示词、上下文变化时知道"是不是变差了"。**

---

## 一、为什么需要评测

2026 年的模型迭代节奏是"每 1–2 个月一代"。这意味着：

- 你上周调好的 prompt / 上下文，可能因为模型升级而失效；
- 新模型在平均分上更强，但在**你的具体任务**上可能更差；
- Agent 的行为是多步的，错一步就全错，靠人眼看几只 case 无法判断稳定性；
- 团队要选型、要采购、要向管理层解释"为什么用这个模型"，都需要证据。

评测（Evals）就是把"感觉还行"变成"有数据、可回归、可解释"的工程实践。

---

## 二、四层评测体系

| 层级 | 评什么 | 频率 | 产出 |
|------|--------|------|------|
| **① 公开榜单** | 模型通用能力、行业水位 | 模型发布时 | 选型初筛 |
| **② 团队任务集（Golden Set）** | 你的真实业务任务 | 每次模型/提示词变更 | 准确率、通过率、成本 |
| **③ 上线前回归** | 端到端流程、工具调用、边界情况 | 每次发版 | 回归报告、阻断项 |
| **④ 线上可观测** | 真实用户使用、失败分布、成本 | 持续 | 监控面板、告警 |

公开榜单只能做初筛，**不能替代 ②③④**。这是团队最常犯的错误。

---

## 三、2026 年主流榜单怎么读

| 榜单 | 测什么 | 适合回答 | 局限 |
|------|--------|----------|------|
| [LMArena / Arena.ai](https://lmarena.ai) | 人类盲测偏好（Elo 式评分） | "大众觉得哪个回答更好" | 偏好不等于正确；任务分布偏聊天 |
| [SWE-bench](https://www.swebench.com) | 解决真实 GitHub Issue | "代码修复能力" | 任务偏 Python 仓库；存在污染争议；Verified 子集更可信 |
| [Artificial Analysis](https://artificialanalysis.ai) | 综合智能指数 + 速度 + 价格 | "质量/成本/延迟怎么权衡" | 指数权重是人为设定；不同 effort 档位不可直接比 |
| [Epoch AI（ECI）](https://epoch.ai) | 50+ 基准的综合能力指数 | "长期趋势、能力水位" | 综合分会掩盖任务差异 |
| [Vals AI](https://vals.ai) | 金融/法律/税务/编码等职业任务 | "专业场景谁更强" | 任务集偏美国语境 |
| [Terminal-Bench](https://www.tbench.ai) | 终端/Agent 任务 | "Agent 执行能力" | 覆盖范围有限 |

### 读榜的四条纪律

1. **看版本和日期**：同一榜单不同版本不可横比（如 AA Index 从 v3 到 v4 权重会变）。
2. **看 effort / thinking 档位**：高推理档的分数不能和标准档直接比。
3. **看子项，不看平均分**：代码、数学、Agent、多模态的排名经常完全不同。
4. **看成本与延迟**：一个贵 10 倍、慢 3 倍的第一名，未必是团队的最优解。

> 📌 截至 2026-10 的参考：Epoch ECI 上 Claude Opus 5.5（167.3）与 GPT-6 Astra（166.4）接近；Gemini 4 Argon 在 Arena 文本偏好上领先。具体数字会变，请以榜单当日数据为准。
> 来源：[Wikipedia · Comparison of generative AI models](https://en.wikipedia.org/wiki/Comparison_of_generative_AI_models)（2026-10 快照）

## 四、建自己的评测集（最重要的一步）

### 步骤

1. **收集真实任务**：从工单、代码评审、客服记录、内部问答里抽取 30–100 条，覆盖常见与边界情况。
2. **写清期望**：每条任务给出"好答案的标准"（rubric），能自动判定的就写判定逻辑，不能的写人工标准。
3. **建基线**：当前生产方案跑一遍，记录准确率、成本、延迟。
4. **变更即回归**：换模型、改 prompt、加工具、改上下文，都跑同一套评测，对比基线。
5. **版本化**：评测集和结果都进仓库，注明日期与模型版本。

### 判定方式

- **精确匹配 / 规则判定**：分类、抽取、格式类任务，优先用这个，便宜且稳定。
- **LLM-as-judge**：让另一个模型按 rubric 打分。必须做**人工校准**（抽 10–20% 人工复核一致性），否则只是把偏见换了个地方。
- **人工评审**：高价值、低样本量场景，用双人盲评。

### 一个最小可用的评测配置

```yaml
# evals/product-qa.yaml
dataset: evals/data/product-qa.jsonl   # 40 条真实问题 + 参考答案要点
metrics:
  - exact_match        # 结构化字段
  - judge_score        # LLM-as-judge，1-5 分
  - cost_per_case
  - latency_p95
baseline: 2026-11-claude-sonnet-5.5
```

## 五、Agent 评测和普通 LLM 评测不一样

Agent 多步执行、调用工具，评测要覆盖：

| 维度 | 问题 | 指标示例 |
|------|------|----------|
| **任务完成** | 最终目标达成了吗？ | 通过率 / pass@k |
| **过程正确** | 工具选对了吗？步骤合理吗？ | 轨迹检查、工具调用准确率 |
| **稳定性** | 同一任务跑 5 次结果一致吗？ | 方差、失败率 |
| **成本** | 完成一个任务花多少 token/时间？ | 每任务成本、耗时 |
| **安全** | 有没有越权、泄露、破坏性操作？ | 违规率、拦截率 |

建议：**同一任务至少跑 3–5 次**，看分布而不是单次结果。Agent 的随机性远大于单轮问答。

## 六、线上可观测（很多人漏掉的一层）

上线后要能回答：

- 哪些请求失败了？失败模式是什么（工具错误 / 上下文超限 / 幻觉 / 拒绝）？
- 每次调用的 token、成本、延迟分布如何？
- 用户是否在重复问同一个问题（说明回答没解决）？
- 模型/供应商切换后，指标有没有漂移？

实践：给每次调用打 trace（输入摘要、模型版本、工具调用链、耗时、成本），按周聚合。没有 trace 的 Agent 系统等于黑盒。

## 七、常见陷阱

| 陷阱 | 说明 | 对策 |
|------|------|------|
| 只看公开榜单选型 | 榜单任务和你的业务不同 | 建团队 Golden Set |
| 样本太少 | 5 条 case 的"90% 准确率"没有意义 | ≥30 条，覆盖边界 |
| 单次运行下结论 | Agent 方差大 | 多次运行 + 看分布 |
| judge 不校准 | LLM 评委有偏好 | 人工抽检一致性 |
| 忽略成本/延迟 | 效果略好但贵 10 倍 | 把成本列为指标 |
| 评测集泄漏进训练 | 数据污染 | 定期换新样本、保留私有集 |
| 换模型不回归 | 行为漂移无人发现 | CI 自动化回归 |

## 八、历史沿革

- **2020–2022**：MMLU、GSM8K 等学术基准主导，主要看"知识/推理"。
- **2023**：Chatbot Arena（后更名 Arena.ai）用人类偏好排序；基准污染问题被广泛讨论。
- **2024**：SWE-bench 成为代码能力黄金标准；Agent 评测开始出现（WebArena、Terminal-Bench 等）。
- **2025**：推理模型让"effort 档位"成为变量；LLM-as-judge 普及；企业开始建内部 eval。
- **2026**：评测走向"职业任务 + 综合指数"（Vals Index、AA Intelligence Index v4、Epoch ECI）；Agent 的轨迹评测、成本评测成为标配；评测与可观测性合并成"质量闭环"。
