# ⭐️ M5-10 · 代码审查与质量控制

> 📅 内容基准：2026-11 ｜ ⏱️ 时效性：中 ｜ 🔁 下次复核：2027-05
>
> AI 生成的代码不等于正确的代码。学会用 AI 辅助 review，而不是无脑信任，才是正确姿势。
>
> 2026 年的变化：Agent 能一次改几十个文件，review 的重点从"看 diff"扩展到"审过程、审证据、审权限"。

---

## AI 生成代码的常见问题

### 🐛 功能性问题
| 问题类型 | 例子 |
|---------|------|
| **逻辑错误** | 边界条件处理不当、off-by-one 错误 |
| **过时 API** | 使用已废弃的方法或旧版本语法 |
| **幻觉依赖** | 引用不存在的库或方法 |
| **并发问题** | 竞态条件、死锁，AI 经常忽略 |

### 🔒 安全漏洞
| 漏洞 | 描述 |
|------|------|
| **SQL 注入** | 字符串拼接 SQL 而非参数化查询 |
| **XSS** | 未转义用户输入直接渲染 |
| **硬编码密钥** | API Key 写在代码里 |
| **不安全的反序列化** | pickle、eval 等危险操作 |
| **权限控制缺失** | 忘记加认证/鉴权 |

### 📉 质量问题
- 没有错误处理（只有 happy path）
- 没有日志
- 命名不符合项目规范
- 测试覆盖不足
- 注释与实际代码不符

## 如何 Review AI 生成的代码

### 分层审查法

**第一层：能跑起来吗？**
```bash
# 先跑起来再说
python xxx.py
# 看有没有明显报错
```

**第二层：逻辑对吗？**
- 手动 trace 关键路径
- 重点看条件判断、循环边界
- 问自己：极端输入（空值、超大值、特殊字符）会怎样？

**第三层：安全吗？**
- 搜索关键词：`eval`、`exec`、`pickle`、字符串拼接 SQL
- 检查所有外部输入是否有验证

**第四层：符合项目规范吗？**
- 命名风格
- 错误处理方式
- 日志格式

## 用 AI 辅助 Review AI 代码

让 AI 自己找自己的问题：

```
Prompt 模板：

请 review 以下代码，重点检查：
1. 安全漏洞（SQL注入、XSS、硬编码密钥等）
2. 边界条件和错误处理
3. 并发安全性
4. 是否有过时或不存在的 API

[粘贴代码]
```

**分角色 Review：**
```
你是一个安全专家，专注于找代码中的安全漏洞，请审查以下代码...

你是一个性能工程师，专注于找代码中的性能问题...

你是一个 Python 资深工程师，检查代码是否符合 PEP8 和最佳实践...
```

## AI 写代码 + AI 写测试

这是目前最高效的工作流之一：

```
Step 1: 让 AI 生成功能代码
"帮我写一个用户注册函数，需要验证邮箱格式和密码强度"

Step 2: 让 AI 生成测试用例（包含边界情况）
"为上面这个函数写 pytest 测试，要覆盖：
- 正常注册
- 邮箱格式错误
- 密码太短
- 密码没有特殊字符
- 重复注册"

Step 3: 跑测试，让测试发现代码问题

Step 4: 把失败的测试发回给 AI 修复
"这个测试失败了：[错误信息]，请修复代码"
```

**为什么有效：**
- AI 知道自己的代码，所以能写出针对性的测试
- 测试用例往往比代码本身更全面
- 形成"代码-测试"闭环，自动发现问题

## 不能无脑信任 AI 的场景

### 🚨 高风险场景，必须人工细审
- **涉及钱的逻辑**：支付、计费、退款
- **权限控制代码**：登录、鉴权、数据隔离
- **数据库 Migration**：字段变更、数据迁移
- **并发 / 分布式**：锁、事务、消息队列
- **密码学相关**：加密、签名、Token 生成

### ✅ 可以放心用 AI 的场景
- 样板代码（CRUD、路由、序列化）
- 正则表达式生成
- 单元测试骨架
- 文档和注释
- 代码格式化和重构

## 团队 AI 代码质量规范建议

```markdown
# 团队 AI 使用规范

## 代码提交要求
- AI 生成的代码必须经过本地测试
- 安全敏感模块（支付、鉴权）禁止直接使用 AI 生成代码
- PR 描述中标注"AI辅助生成"便于 reviewer 重点关注

## Review 重点
- AI 生成代码 review 时间不得少于手写代码
- 安全相关代码需额外 reviewer 确认

## 测试要求
- AI 生成的函数必须有对应测试用例
- 测试覆盖率不低于项目平均水平
```

## Agent 时代的 Review：审过程，而不只是审结果

当 AI 一次提交几百行、跨十几个文件，逐行读 diff 已经不现实。更有效的做法是把 review 拆成三个门：

```
① 计划门：改哪些文件、为什么改、怎么验证？（写代码前确认）
② 过程门：Agent 用了什么工具、跑了什么测试、证据在哪？
③ 结果门：diff 是否符合规范、测试是否通过、风险是否可控？
```

**证据优先原则**：Agent 说"已修复"不算数，要给出可复现的证据——测试输出、复现步骤、运行日志。没有证据的"完成"一律视为未完成。

### 审查 Agent 产出的十个问题

1. 需求边界清楚吗？有没有顺手改了不该改的文件？
2. 有没有跳过测试、注释掉失败用例、放宽断言？
3. 新增依赖是否必要、是否可信？
4. 错误处理和边界条件覆盖了吗？
5. 是否引入了重复实现（项目里已有同样功能）？
6. 安全敏感代码（鉴权、支付、迁移、并发）是否人工细审？
7. 提交信息、PR 描述是否说明了"为什么"？
8. 测试是否真的验证了行为，而不是验证了实现？
9. 回滚方案是什么？数据库变更能否安全回退？
10. 有没有把密钥、内部数据、调试代码带进提交？

### 自动化门禁（Agent 提效的前提）

- **格式 / Lint / 类型检查**：CI 必须全绿
- **单元测试 + 覆盖率阈值**：关键路径必须有测试
- **SAST / 依赖漏洞扫描**：把安全问题挡在合并前
- **AI reviewer 作为"第一读者"**：让另一个模型先过一遍，人只看它标记的高风险点与最终决策
- **分支保护 + 人工审批**：危险模块不允许 Agent 直接合入

> 💡 一个反直觉的结论：Agent 越强，**测试和 CI 越重要**。因为代码产出速度远超人工审查速度，唯一能跟上的"审查者"是自动化验证。

## 历史沿革

- **2023**：关注"AI 写的代码对不对"，主要靠人工读 diff + 单测。
- **2024**：Cursor/Copilot 进入日常，出现"AI 写、AI 测、人抽查"的闭环。
- **2025**：Agent 化让单次改动规模变大，TDD / 计划评审重新受重视；AI reviewer 工具出现。
- **2026**：Review 重点转向"过程与证据"：计划门、过程门、结果门；自动化门禁成为 Agent 提效的前提；Agent Teams 里出现"子 Agent 写、另一个 Agent 审"的分工。
