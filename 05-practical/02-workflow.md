# M5-02 · Agentic 开发工作流

> 📅 内容基准：2026-11 ｜ ⏱️ 时效性：中 ｜ 🔁 下次复核：2027-05
>
> 把 AI 真正融入日常开发流程。2026 年的关键词不是"补全"，而是 **Spec → Plan → 子 Agent 执行 → Review → 验证**。

---

## 2023 的工作流，为什么不够用了？

2023-2024 年，主流用法是"在 IDE 里让 AI 补全 + 聊天问问题"，AI 是**副驾驶**。

2026 年，Agent 能读仓库、跑命令、改多个文件、开子 Agent 并行工作。工作流的核心矛盾变了：

| 旧问题 | 新问题 |
|--------|--------|
| 代码补全不准 | Agent 一次改太多，review 不过来 |
| 不知道怎么写 Prompt | 需求和验收没说清，Agent 自信地做错 |
| 单文件修改 | 多文件、跨模块、并发修改冲突 |
| 人工测试 | 需要自动验证 + 回归评测 |
| 偶尔用一下 | 权限、成本、审计、可回滚 |

所以 2026 年的工作流，重点从"怎么让 AI 写代码"变成"**怎么让 AI 在可控边界内可靠地交付**"。

---

## 2026 推荐工作流（总览）

```
0. 准备（Prep）
   AGENTS.md / 干净 Git / 基线测试 / 权限与预算
        ↓
1. 规格（Spec）
   目标 + 范围 + 验收标准 + 非目标
        ↓
2. 计划（Plan）
   Plan Mode 只读探索 → 任务拆解 → 人工确认
        ↓
3. 执行（Execute）
   主 Agent 编排 → 子 Agent 并行（写作用域互不重叠）
        ↓
4. 审查（Review）
   Diff 审查 → AI Review → 人工 Review
        ↓
5. 验证（Verify）
   测试 / Lint / 类型 / E2E / 安全 / 评测
        ↓
6. 交付（Ship）
   PR 描述 / CHANGELOG / 回滚方案 / 监控
```

---

## 阶段 0：准备

### 项目上下文文件

2026 年的通行做法是 **AGENTS.md**（跨工具开放格式）：

```markdown
# AGENTS.md

## 项目概览
- 后端：FastAPI + SQLAlchemy 2.0
- 前端：React + TypeScript
- 测试：pytest / vitest

## 常用命令
- 安装：pnpm install
- 开发：pnpm dev
- 测试：pnpm test
- Lint：pnpm lint

## 约定
- Python 用 type hints，异步优先
- 错误统一用自定义异常
- 提交前必须跑 lint + test

## 禁止
- 不要改 migrations/ 下的历史文件
- 不要提交 .env
```

> AGENTS.md 已被 6 万+ 开源项目采用，由 Agentic AI Foundation 托管（来源：[agents.md](https://agents.md/)，2026-11）。Claude Code 的 `CLAUDE.md`、Cursor 的 rules 也是同类思路，可按团队工具选择。

### 其他准备

- **Git 干净**：先 commit/stash，Agent 改坏了能一键回滚
- **基线测试**：先跑一遍测试，确认"改之前是绿的"
- **权限最小化**：只给需要的目录、只读优先、写操作审批
- **预算**：设置 Token/金额/步数上限
- **隔离环境**：worktree / 容器 / 分支，避免污染主工作区

## 阶段 1：规格（Spec）

先把"要做什么"写成可验收的文档，再让 Agent 动手。2026 年流行的 **Spec-Driven Development** 就是这个思路。

```markdown
# Spec: 用户积分系统

## 目标
用户完成订单获得积分，积分可抵扣，有有效期。

## 范围
- 修改：services/points.py、api/points.py、models/point.py
- 不修改：支付核心链路、auth 模块

## 非目标
- 不做积分商城
- 不做跨账号转移

## 验收标准
- [ ] 订单完成后按金额 ×10 发放积分
- [ ] 100 积分 = 1 元抵扣
- [ ] 同一订单重复回调不重复发放（幂等）
- [ ] 积分 1 年后过期
- [ ] 并发扣减不超发
- [ ] 单元测试 + 集成测试通过

## 风险
- 并发扣减需要事务/乐观锁
- 历史数据迁移需要单独脚本
```

> 判断标准：**两个工程师看完能得出同一结论**，才算合格 Spec。含糊的 Spec 会变成 Agent 的"自由发挥空间"。

## 阶段 2：计划（Plan）

### Plan Mode：先只读，不动手

2026 年主流编码 Agent 都提供"计划模式"：Agent 只能读代码、搜索、分析，产出计划，**不写文件**。人确认后再进入执行。

```
Plan 输出应包含：
1. 涉及哪些文件/模块
2. 修改顺序与依赖关系
3. 风险点与回滚方案
4. 验证方式（跑哪些测试/命令）
5. 预计工作量与可并行部分
```

### 人工确认清单

- [ ] 计划覆盖了所有验收标准
- [ ] 没有改到"禁区"（支付、权限、迁移文件）
- [ ] 验证方式可执行，不是"跑一下看看"
- [ ] 任务粒度足够小（每步可独立 review）
- [ ] 明确了停止条件（何时该停下来问人）

> **这是整个流程里最值得花时间的一步。** 计划错了，执行越快越糟。

---

## 阶段 3：执行

### 单 Agent：小步、可验证

```
1. 按计划改一小块
2. 跑相关测试
3. 通过 → commit（或 checkpoint）
4. 不通过 → 修，不要继续堆功能
5. 重复直到完成
```

### 多 Agent：写作用域必须互不重叠

```
主 Agent（编排）
  ├─ 子 Agent A：后端 models/services（worktree A）
  ├─ 子 Agent B：前端组件（worktree B）
  └─ 子 Agent C：测试与文档（worktree C）
        ↓
主 Agent 汇总 diff、跑集成测试、处理冲突
```

原则：
- **一个文件同一时间只让一个 Agent 写**
- 子 Agent 返回**摘要 + diff + 验证结果**，不要把过程全塞回主上下文
- 用 **git worktree / 分支**隔离，避免互相覆盖
- 合并前由主 Agent 或人统一跑测试

### 并行要克制

不是所有任务都适合并行。依赖关系强、需要频繁讨论、改动同一模块的任务，串行更快也更省。

## 阶段 4：审查

### 三层审查

| 层级 | 谁做 | 看什么 |
|------|------|--------|
| **自审** | 写代码的 Agent | Diff 是否只改了该改的；有没有调试残留 |
| **AI Review** | 另一个 Agent / 工具 | 安全、并发、性能、边界条件 |
| **人工 Review** | 人 | 需求是否真的满足；架构是否合理；能否维护 |

### Diff 纪律

- 一次 PR 只做一件事，**控制 diff 体积**
- 拒绝"顺手重构"混进功能 PR
- 重点看：权限校验、错误处理、事务边界、日志、配置
- 生成的代码也要过和人类代码一样的 review 标准

> 2026 年最常见的翻车不是"AI 不会写"，而是"AI 写了 800 行，没人认真看"。

## 阶段 5：验证

### 自动化门禁

```bash
# 最小集合
pnpm lint
pnpm test
pnpm typecheck

# 更完整的门禁
pnpm test:e2e
pnpm test:integration
pnpm audit            # 依赖漏洞
python3 scripts/check_security.py
```

### Agent 任务的专项验证

- **行为验证**：跑真实命令，看最终状态，不只看模型说"完成了"
- **回归测试**：确认旧功能没坏
- **评测集**：对 Agent 输出跑固定任务集（见 [M4-06](../04-principles/06-evaluation.md)）
- **安全验证**：权限、注入、敏感信息、依赖供应链

### 环境

本地 → CI → 预发 → 生产，逐级验证。Agent 产出不跳过任何一级。

---

## 阶段 6：交付

- **PR 描述**：变更摘要、验证方式、风险与回滚
- **CHANGELOG**：团队可见的变更记录
- **监控**：上线后看错误率、延迟、成本
- **回滚预案**：功能开关 / revert / 数据库回滚脚本

```
PR 模板：
## 做了什么
## 为什么
## 怎么验证（命令/截图）
## 风险与回滚
## AI 参与说明（哪些是生成的、人改了什么）
```

## 工具对照（2026-11）

| 环节 | 常见工具/做法 |
|------|--------------|
| 项目上下文 | AGENTS.md / CLAUDE.md / Cursor Rules |
| 规格与计划 | GitHub Spec Kit（Specify → Plan → Tasks → Implement → Converge）、各工具的 Plan Mode |
| 执行 | Claude Code、Codex、Cursor、Copilot、Gemini CLI、OpenCode 等 Agent |
| 并行隔离 | git worktree、分支、容器 |
| 审查 | AI Review + 人工 Review + 静态分析 |
| 验证 | CI、测试框架、评测集、安全扫描 |
| 观测 | 日志、Tracing、成本监控 |

> GitHub Spec Kit 已提供 40+ 编码 Agent 集成，核心流程是 **Specify → Plan → Tasks → Implement → Converge**（来源：[Spec Kit 文档](https://github.github.io/spec-kit/)，2026-11-04）。工具会变，流程思想更稳定。

## 团队协作规范建议

| 场景 | 建议 |
|------|------|
| AI 生成的代码 | 照常走 Code Review，作者对质量负责 |
| AI 写的注释/文档 | 确认准确性，错误注释比没注释更糟 |
| 敏感数据 | 脱敏后再发给 AI；优先用企业版/私有部署 |
| 权限 | 最小权限；生产写操作必须人工审批 |
| 成本 | 按任务选模型档位；设置预算告警 |
| 工具选型 | 团队统一，避免"每人一套配置" |
| 审计 | 记录谁在什么上下文让 Agent 做了什么 |

## 什么时候不要用 Agent？

| 场景 | 原因 | 替代 |
|------|------|------|
| 需求完全不清楚 | Agent 会"自信地做错" | 先和人把 Spec 写清 |
| 没有测试/无法验证 | 无法判断对错 | 先补测试或人工验证方案 |
| 高风险不可逆操作 | 删库、转账、生产配置 | 人工执行 + 双人复核 |
| 强合规/强审计场景 | 需要可解释的责任链 | 受控自动化 + 人工签字 |
| 一次性小改动 | Agent 启动成本更高 | 直接改 |

> 原则：**能用确定性脚本/工作流解决的，不要用 Agent。** Agent 适合"步骤不确定、需要判断"的任务。

---

## 历史沿革

- **2026**：Spec → Plan → 子 Agent 执行 → Review → 验证 成为主流；AGENTS.md、Spec Kit、Plan Mode、Agent Teams 普及；评测与权限治理进入工作流。
- **2024-2025（旧版流程）**：需求理解 → 方案设计 → 编码（Chat/Agent/Tab）→ 调试 → 测试 → Code Review → 上线，AI 主要作为"副驾驶"嵌入各阶段；`.cursorrules` 是主要上下文载体。旧流程仍有参考价值，但缺少并行隔离、自动验证与权限边界。
- **2023**：以 Chat 问答 + 代码补全为主，"让 AI 写一段代码"是核心用法。
