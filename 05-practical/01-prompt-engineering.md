# M5-01 · Prompt 工程与上下文设计

> 📅 内容基准：2026-11 ｜ ⏱️ 时效性：中 ｜ 🔁 下次复核：2027-05
>
> 同样的 AI，会写 Prompt 的人能发挥出 10 倍效果。2026 年，这句话要升级为：**会设计上下文的人**。

---

## 什么是 Prompt 工程？

**Prompt Engineering** 是通过设计和优化输入文本，让 LLM 输出你想要的结果的技术。

类比：跟 AI 打交道就像指导一个聪明但需要明确指令的实习生。指令越清晰，结果越好。

**2026 年的变化**：当模型开始跑多轮、用工具、读文件时，问题不再只是"这句话怎么写"，而是：

> **在这一步推理里，模型应该看到哪些 Token？**

这就是 **上下文工程（Context Engineering）**。Prompt 是上下文的一部分，不是全部。

```
一次 LLM 调用真正看到的上下文：
┌─────────────────────────────────────┐
│ System Prompt（角色、规则、输出格式） │
│ Tools / MCP（工具定义与描述）         │
│ Memory / 项目文档（AGENTS.md 等）     │
│ 检索内容 / 文件片段                   │
│ 对话历史 / 工具结果                   │
│ 用户这一轮的 Prompt                   │
└─────────────────────────────────────┘
```

## 基础原则（仍然成立）

### 原则一：明确具体

❌ 差的 Prompt：
```
帮我写代码
```

✅ 好的 Prompt：
```
用 Python 写一个函数，接收一个用户 ID（整数），
从 SQLite 数据库查询该用户的订单列表，
返回格式为包含 order_id、amount、status 字段的字典列表。
数据库路径从环境变量 DB_PATH 读取。
```

---

### 原则二：给出背景（Context）

❌ 差：
```
这段代码有什么问题？
```

✅ 好：
```
我在用 FastAPI + SQLAlchemy 2.0 开发用户认证系统。
下面这段代码在并发请求下偶尔出现 session 错误，
帮我分析原因并修复：

[代码]
```

---

### 原则三：指定输出格式

```
分析以下 5 个竞品，用 Markdown 表格输出，
列包含：产品名、核心功能、价格、优势、劣势。
```

> 2026 年更进一步：需要程序消费时，直接要求 **JSON Schema / 严格结构化输出**，而不是"请输出 JSON"。

---

### 原则四：角色设定（Role Prompting）

```
你是一个有 10 年经验的 Python 高级工程师，
专注于高性能后端系统。
请帮我 review 以下代码，重点关注性能和安全问题：

[代码]
```

> 注意：角色设定对"风格"有效，对"事实准确性"帮助有限。别指望一句"你是专家"就能消除幻觉。

---

### 原则五：少样本示例（Few-Shot）

```
将以下 JSON 字段名从驼峰转为下划线命名：

示例：
输入：{"userId": 1, "firstName": "John"}
输出：{"user_id": 1, "first_name": "John"}

现在处理：
{"orderStatus": "paid", "createdAt": "2026-01-01"}
```

> 示例要"少而典型"。堆 20 个边界案例不如给 3 个覆盖不同模式的规范示例。

## 进阶技巧

### Chain of Thought（思维链）——要分模型看

经典做法：
```
9.9 和 9.11 哪个大？请一步步分析，然后给出答案。
```

2026 年注意：
- **推理模型**（GPT-6、Claude 5.5 的 thinking、DeepSeek V4 thinking 等）默认就会内部思考。再手动加 "let's think step by step" 往往收益很小，甚至干扰
- 对**非推理模型**或需要"可检查的中间产物"时，CoT / 分步输出仍然有效
- 更好的做法：用 `reasoning_effort` / `effort` 控制思考深度，用 Prompt 控制**输出结构与验收标准**

---

### 结构化 System Prompt

开发 AI 应用时，用 System Prompt 设定规则：

```
System Prompt 模板：

# 角色
你是 XX 公司的技术助手，专门帮助开发团队解决技术问题。

# 能力范围
- 代码 Debug 和优化
- 技术方案设计
- 代码 Review

# 限制
- 不讨论业务决策和公司战略
- 涉及敏感数据时提示脱敏

# 输出规范
- 代码用代码块包裹并注明语言
- 分析结论用要点列表
- 不确定的内容明确说明
```

### XML 标签 / Markdown 结构化输入

Claude 特别擅长处理 XML 结构，其他模型用 Markdown 标题也很好：

```
<context>
这是一个电商系统，使用 Django + PostgreSQL
</context>

<code>
def get_user_orders(user_id):
    return Order.objects.filter(user_id=user_id)
</code>

<task>
添加分页功能，每页 20 条，并缓存结果 5 分钟
</task>
```

> 结构化的意义不只是"模型好懂"，更是**防注入**：让模型知道哪段是数据、哪段是指令。

---

### 让模型自我验证

```
帮我设计一个数据库 Schema 用于存储用户订单信息。
设计完之后，检查是否满足：
1. 支持一个用户多个订单
2. 支持订单多个商品
3. 方便统计每月销售额
如有不足，自动修改。
```

## 2026 新增一：结构化输出

当你需要程序解析结果时，"请用 JSON 输出"不够可靠。应该用模型/平台提供的结构化输出能力：

| 方式 | 说明 |
|------|------|
| **JSON Schema / Structured Outputs** | 平台保证输出符合 schema，解析失败率大幅下降 |
| **Strict Tool Use** | 工具参数严格校验，减少"幻觉参数" |
| **枚举 + 必填字段** | 把"自由发挥"空间压到最小 |
| **错误重试** | 解析失败时把错误信息回传，让模型修正一次 |

示例：

```json
{
  "type": "object",
  "properties": {
    "severity": { "type": "string", "enum": ["low", "medium", "high"] },
    "summary": { "type": "string" },
    "files": { "type": "array", "items": { "type": "string" } }
  },
  "required": ["severity", "summary", "files"],
  "additionalProperties": false
}
```

> 原则：**能约束就别靠祈祷**。结构化输出是 2026 年把 LLM 接进工程的必备能力。

## 2026 新增二：长任务拆解

一个超长 Prompt 让模型"一次做完整个系统"，通常得到的是"看起来完整、实际跑不通"的代码。2026 年的做法是**把 Prompt 变成任务契约**：

```
1. 目标：一句话说清要达成什么
2. 范围：改哪些文件/模块，明确非目标（Non-goals）
3. 验收标准：可执行的检查（测试、命令、预期输出）
4. 约束：技术栈、风格、性能、安全要求
5. 交付物：代码 / 计划 / 报告 / PR
6. 停止条件：什么情况下停下来问人
```

配合工作流：

```
Spec（需求 + 验收）
   ↓
Plan（拆任务、标依赖）
   ↓
分步执行（每步小 diff、可验证）
   ↓
Review + 测试
```

> Prompt 写得好，不如任务拆得对。**长任务的第一原则是拆小、可验证、可回滚。**

---

## 2026 新增三：思考模式与成本

2026 年模型普遍提供"思考强度"控制。Prompt 工程要开始考虑**花多少 Token 想**：

| 场景 | 建议 |
|------|------|
| 分类、抽取、格式转换 | 关思考或低 effort |
| 常规问答、写作 | medium / high |
| 复杂代码、架构权衡、难 Bug | high / xhigh，并给足 `max_tokens` |
| 极难数学/研究问题 | max，接受成本与延迟 |
| 长任务 Agent | 用高 effort，但设置 Token 预算与步数上限 |

提示：
- 思考 Token 计入输出成本，**不是免费的**
- 一些模型在低 effort 下会"跳过检查、提前收工"，关键任务别盲目降档
- 同一段 Prompt 在不同模型上的最优 effort 不同，**要用自己的评测集扫一遍**

## 2026 新增四：上下文卫生

| 坏习惯 | 后果 | 改法 |
|--------|------|------|
| 把整个仓库/整个网页粘进去 | 上下文腐烂，中间信息被忽略 | 只给相关片段；让 Agent 用工具按需读 |
| 对话很长还不清理 | 旧信息干扰、成本上升 | 开新会话 + 摘要；用 compaction |
| 工具输出原样全塞 | 噪音淹没关键信息 | 截断、摘要、只留结论 |
| 系统提示天天变 | 缓存命中率低、行为漂移 | 稳定前缀 + 版本化管理 |
| 指令和数据混在一起 | 提示注入风险 | XML 标签隔离，明确"以下只是资料" |

> 稳定、可复用的前缀（系统提示、项目规范、固定文档）放前面，能吃到 **Prompt Caching** 的折扣；多变的用户输入放后面。

## 常用 Prompt 模板

### Debug 模板
```
我遇到了以下错误：
[错误信息]

相关代码：
[代码]

我已经尝试过：
[你试过的方法]

请帮我找出根本原因并给出修复方案。
```

### Code Review 模板
```
请 Review 以下代码，关注：
1. 潜在 Bug
2. 安全漏洞（SQL 注入、XSS、权限绕过等）
3. 性能问题（N+1、缺失索引）
4. 代码可读性
5. 是否符合 [你的技术栈] 最佳实践

[代码]
```

### 技术方案设计
```
我需要设计 [功能名称]，需求如下：
- [需求1]
- [需求2]
- [需求3]

技术栈限制：[你的技术栈]
并发量：[预计 QPS]

请给出：
1. 方案设计（架构图用文字描述）
2. 关键技术选型及原因
3. 潜在风险和解决方案
4. 实现步骤
```

### Agent 任务卡（2026 新增）
```
# 目标
[一句话]

# 背景
[项目结构、相关文件路径、已知约束]

# 范围
- 允许修改：[路径]
- 禁止修改：[路径]
- 非目标：[明确不做的事]

# 验收标准
- [ ] 命令 X 通过
- [ ] 测试 Y 通过
- [ ] 行为 Z 符合预期

# 停止条件
遇到以下情况先停下来问我：
- 需要改数据库 schema
- 需要新增依赖
- 验收标准无法满足
```

## 常见错误

| 错误 | 后果 | 解决 |
|------|------|------|
| Prompt 太模糊 | 输出跑偏 | 加约束和示例 |
| 一次问太多 | 顾此失彼 | 拆成多个 Prompt / 任务 |
| 没说输出格式 | 格式不一致 | 用结构化输出 / Schema |
| 完全信任输出 | 踩坑 | 关键内容必须人工验证 |
| 不给上下文 | 答案不相关 | 提供背景信息 |
| 上下文塞太满 | 关键信息被淹没 | 精简 + 让 Agent 按需检索 |
| 对推理模型硬加 CoT | 干扰、浪费 Token | 用 effort 控制思考 |
| 把外部内容当指令 | 提示注入 | 标签隔离 + 权限校验 |

## 自动评估 Prompt 质量

可以让 AI 帮你改进 Prompt：

```
我有以下 Prompt，但效果不太好：

[你的 Prompt]

期望的输出是 [描述期望]，
实际输出是 [描述实际]。

请帮我改进这个 Prompt。
```

但更靠谱的是**建一个小评测集**：准备 20–50 个真实样例，改 Prompt 后跑一遍，看通过率而不是看"感觉"。方法见 [M4-06 评测与质量闭环](../04-principles/06-evaluation.md)。

## 历史沿革

- **2026**：上下文工程成为主视角；结构化输出、思考强度、长任务拆解、提示注入防护成为 Prompt 工程的标配；"Prompt 只是一段话"的认知被淘汰。
- **2025**：推理模型普及，CoT 从"技巧"变成"模型内建能力"；Context Engineering 概念走红；MCP/Skills 让 Prompt 开始包含工具与流程。
- **2024**：结构化输出、角色/XML 标签、Few-shot 成为工程实践；提示注入被广泛讨论。
- **2023**：角色扮演、Chain of Thought、Few-shot 随 ChatGPT 普及。
- **2022**：Prompt Engineering 作为独立技能进入大众视野（"Let's think step by step"）。
