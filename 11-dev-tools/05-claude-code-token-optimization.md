## 文章核心观点（给团队的 1 分钟版本）

1. **模型没有「接着读」的记忆**，每次都要重新处理完整上下文。  
2. **Prompt Cache 命中时很省钱**，频繁开新会话反而可能更贵。  
3. **缓存失效（尤其大上下文）代价很高**，所以会话管理比「盲目 /clear」更重要。  
4. **最便宜的 Token 是不进上下文的 Token**：少贴大段日志，多给文件路径让工具检索。  
5. **2026-11 补充**：缓存是自动的，但**切模型、改 effort、改规则、压缩**都会影响命中；成本优化 = 减少「前缀变化」。

## 详细要点整理

### 1) 为什么会「烧配额」

Claude Code 每次请求通常要带三类输入：

- 固定前缀（系统提示、工具定义、项目规则）
- 历史对话
- 当前新消息

会话轮次越多，历史内容越大。如果不命中缓存，每轮都会重复付费。

### 2) 缓存机制是省钱关键（2026-11 口径）

Claude Code 的 prompt caching 是**自动**的，按「前缀完全匹配」工作：

- 一轮正常的请求 = 上一轮的全部内容 + 最新一轮；只有新增部分需要重新处理
- **任何前缀变化都会让后面的内容全部重算**（不是按文件/片段缓存）
- 缓存有 TTL（5 分钟 / 1 小时两档），闲置超过 TTL 后恢复会话 = 冷启动

**会破坏缓存的动作（按代价从高到低）：**

| 动作 | 影响 |
|------|------|
| **切换模型** | 每个模型独立缓存，换模型后整段历史无命中 |
| **改系统提示 / 工具定义** | 前缀变化，全部重算 |
| **改 CLAUDE.md / 规则（会话中）** | 不立即生效；重启后才应用 |
| **`/compact` 压缩** | 会话层被摘要替换，下一次请求重建（系统提示/项目上下文可能仍命中） |
| **切换 effort** | 多数模型会重算；但 Opus 5.5 / Sonnet 5.5 / Haiku 5.5 / Fable 5.1 默认保持缓存 |
| **切换 fast mode** | 快/慢两套缓存，切换后第一轮无命中 |
| **MCP 工具增删** | 取决于是否启用 tool search；默认支持时通常不影响 |

> 结论：**不是「永远新会话」，也不是「永远一个会话」，而是按任务与「前缀稳定性」决策。**

### 3) 会话决策原则（可直接执行）

继续当前会话（优先）：

- 任务没变（仍在同一模块/同一问题）
- 会话仍活跃（间隔不长）
- 现有上下文对当前任务仍有价值

开新会话：

- 任务切换（如从认证模块转到支付模块）
- 会话长期闲置后恢复（缓存已过期）
- 上下文噪音明显增多（大量无关试错记录）

### 4) 慎用超大上下文窗口

- 大窗口不是越大越好
- 对日常改 bug / 小重构，通常并不需要极限上下文
- 大上下文在缓存失效后的重建成本更敏感
- 2026 年 Fable / Opus 5.5 / Sonnet 5.5 / Haiku 5.5 等支持 1M 上下文，但**大窗口 ≠ 应该塞满**

### 5) 六条落地建议（团队版）

1. 日常优先使用成本更稳的模型档位（Sonnet 5.5 / Haiku 5.5），复杂任务再升 Opus 5.5 / Fable 5.1。  
2. 避免会话中途频繁切模型（会破坏缓存）；在会话开始时就选好模型与 effort。  
3. 精简项目规则文件，减少每轮固定注入体积；规则改动放到新会话生效。  
4. 能用命令行完成的检索优先命令行，少把长结果直接塞进对话。  
5. 复杂任务先做计划再执行，减少返工轮次。  
6. 用读取权限/路径约束，避免模型扫描无关目录（如 `node_modules`、构建产物）。

## 2026-11 新增：把「缓存」用对的 7 个操作

```bash
/context          # 看当前上下文都装了什么（按类别）
/compact 保留 auth bug 的修复   # 在任务切换处主动压缩，而不是等自动触发
/autocompact 500k # 设置自动压缩阈值（按模型/套餐）
/rewind           # 回到之前某一轮，复用已有缓存
/model            # 会话开始时选好，别中途换
```

1. **模型和 effort 在会话开头就定**：中途换 = 冷启动。  
2. **`/compact` 放在任务自然断点**：自动压缩可能在你正忙时触发；主动压缩更可控。  
3. **重要约束放根级 `CLAUDE.md`**：路径规则、嵌套规则会被压缩摘要掉。  
4. **大读取交给子 Agent**：文件内容留在子上下文，主会话只拿摘要。  
5. **一次性任务用 `/clear` 或新会话**：别让旧任务的历史拖累新任务。  
6. **并行 Agent / Agent Teams 要算总账**：每个 teammate 都是独立实例，token 成本显著更高。  
7. **用 `rtk` 压缩命令输出**：见 [M11-01](./01-rtk-token-killer.md)，从源头减少进入上下文的 token。

## 价格锚点（2026-11，帮助估算成本）

| 模型 | 输入（/MTok） | 输出（/MTok） | 缓存读（/MTok） |
|------|--------------|--------------|----------------|
| **Opus 5.5** | $4 | $20 | $0.20 |
| **Sonnet 5.5** | $2 | $10 | $0.10 |
| **Haiku 5.5**（≤100K） | $0.10 | $0.50 | $0.01 |
| **Fable 5.1** | $10 | $50 | $0.25 |

> 来源：[claude.com/pricing](https://claude.com/pricing)（2026-11 核对）。缓存读通常占 Agent 编码成本的绝大部分，所以**提高缓存命中率比换更便宜的模型更有效**。

## 给你团队的「立即可用」操作清单

1. 把「会话切换规则」写进团队规则（任务切换才新开会话）。  
2. 统一日志处理习惯：给路径，不贴万行日志。  
3. 每周复盘一次「高成本会话」，找出冗余上下文来源。  
4. 给项目加目录读取边界，减少无关扫描。  
5. 会话开头定好模型 / effort，避免中途切换。  
6. 在任务断点主动 `/compact`，重要约束放根级 `CLAUDE.md`。  
7. 大文件/大搜索交给子 Agent，或先用 `rtk` 压缩。
