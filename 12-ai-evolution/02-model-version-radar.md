# M12-02 · 模型版本迭代追踪法

> 新模型发布时，不要只看发布会标题，也不要只看一个榜单分数。团队需要一套固定问题，判断它到底值不值得切换。
>
> 最后更新：2026年6月

---

## 新模型发布后先问 7 个问题

| 问题 | 为什么重要 |
|------|------------|
| 1. 它解决了什么旧问题？ | 是真实升级，还是营销包装 |
| 2. 哪个能力变强？ | 推理、代码、多模态、长上下文、速度、成本 |
| 3. 哪些场景会受益？ | 不能只说“全面更强” |
| 4. 是否改变价格结构？ | 输入、输出、缓存、长上下文都要看 |
| 5. 是否改变上下文窗口？ | 长上下文可能更贵，也可能让结果变差 |
| 6. 是否改变工具调用能力？ | Agent 能力很大程度取决于工具可靠性 |
| 7. 是否值得迁移默认模型？ | 迁移有学习成本和稳定性风险 |

---

## 不再维护“固定排行榜”的原因

模型版本变化太快，固定写死这些内容很容易误导：

- 某模型排名第一
- 某模型具体跑分
- 某 API 固定价格
- 某版本绝对最强

更好的做法是维护：

- 官方入口
- 评测入口
- 团队自己的试用结论
- 适合/不适合场景

---

## 团队自己的模型雷达

建议团队内部维护一张轻量表：

| 模型/版本 | 主要变化 | 适合场景 | 风险 | 是否试点 | 结论 |
|-----------|----------|----------|------|----------|------|
| 新模型 A | 代码更强 | 后端重构 | 成本未知 | 是 | 待评估 |
| 新模型 B | 更便宜 | 批量摘要 | 质量略低 | 是 | 可用于低风险任务 |

这张表不用追求全网最全，只追求对团队有用。

---

## 评估新模型的最小实验

每次新模型发布，不建议直接全员切换。先用 3 类任务小测：

1. **日常任务**：解释代码、写简单函数、生成文档
2. **困难任务**：跨文件重构、复杂 Bug、架构取舍
3. **团队真实任务**：拿一个历史 Issue 或 PR 重跑

记录：

- 成功率
- 返工次数
- 输出是否可读
- 是否愿意直接交给它做下一次任务
- 成本是否可接受

## 一句话原则

> 新模型不是“发布了就换”，而是“先用团队真实任务验证，再决定放到哪个场景里”。
